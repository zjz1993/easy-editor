# Spec 模式开发流程（必读）

从本文件启用之日起，**编辑器的新需求开发一律采用 spec 模式**：先写规格、确认后再编码、按验收标准交付。禁止跳过 spec 直接动手写代码。

## 流程总览

```
需求描述
  → ① 撰写 spec（AI 起草）
  → ② grill-with-docs 追问，确定需求（可多轮）
  → ③ 用户确认 spec 最终稿
  → ④ 拆解任务清单 tasks
  → ⑤ 按 spec 实现（过程中 spec 有变需同步改文档并告知用户）
  → ⑥ 对照验收标准逐条自检 + 常规验证（react-doctor、build、demo）
  → ⑦ 交付时报告 spec 验收结果
```

### 用 grill-with-docs 确定需求（② 的标准做法）

spec 起草后、用户确认前，**默认调用 `grill-with-docs` skill 对 spec 进行盘问**，把模糊点逐个问清：

- 盘问对象是当前 `.ai/specs/<...>/spec.md`，重点针对「开放问题」「边界情况」「非目标」三个章节
- skill 产生的文档更新（决策、术语澄清）**写回本需求的 spec.md**，不要另建 CONTEXT.md / ADR
- 每轮追问后同步修订 spec，直到没有悬而未决的分支，才进入用户最终确认（③）
- 用户明确说“不用问了，直接确认”时可跳过盘问

## 目录约定

每个需求一个目录，放在 `.ai/specs/` 下：

```
.ai/specs/<YYYY-MM-DD>-<需求短名>/
├── spec.md      # 规格文档（必需）
└── tasks.md     # 任务拆解（spec 确认后生成，可选）
```

例：`.ai/specs/2026-08-17-character-count/spec.md`

## spec.md 必须包含的章节

使用 `.ai/specs/TEMPLATE.md` 起草，至少涵盖：

1. **背景与目标**：为什么做，解决什么问题
2. **非目标**：明确不做什么，防止范围蔓延
3. **交互 / 视觉描述**：用户看到什么、怎么操作（有设计稿贴链接或截图）
4. **技术方案**：涉及的包、扩展、API / props 设计、数据结构
5. **边界情况**：空态、极端数据、与其他功能的冲突（列表、表格、拖拽、撤销等）
6. **兼容性影响**：是否改 `<Editor>` props、是否影响既有用户
7. **验收标准**：可逐条勾选的 checklist，作为交付依据

### 模板的使用边界（骨架固定，内容自由）

- 上述章节是**硬性骨架**：一节都不能缺，尤其是「非目标」「验收标准」「开放问题」——它们分别是防范围蔓延、交付依据、盘问对象的抓手。
- 章节内**详略自由**：小需求每个章节两三句话即可，不必灌水；复杂需求（跨多包、改 props 形态、涉及拖拽/撤销等全局行为）则必须写透。
- 允许在骨架之外增加需求特有的章节（如性能指标、埋点、迁移方案），但不允许删减或合并掉骨架章节。

## 硬性规则

- **spec 未经用户确认，不得开始写实现代码**。确认方式：用户明确回复同意（如“确认”、“按这个做”）。确认前默认先经 `grill-with-docs` 盘问（见上）。
- 用户只给一句话需求时，AI 不得自行脑补细节直接开发，必须先产出 spec 并通过盘问补齐关键决策。
- 实现中途需求有变：先改 spec.md（并在交付说明中指出改动点），再改代码，保持文档与实现一致。
- **验收标准未全部勾选前，不得宣告需求完成**。
- 交付时必须附上验收 checklist 的逐条结果，而不是只说“做完了”。
- spec 模式不替代既有验证流程：react-doctor、build、demo 同步等约束照常执行。

## 适用范围

- **适用**：新功能、交互改版、涉及多包或 props 形态变更的需求
- **可豁免**（无需 spec，但仍走常规验证）：修 typo、单点 bugfix（原因明确）、纯文档、样式微调
