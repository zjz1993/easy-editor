# 性能与大文档

本文回答一个常见问题：**编辑器能流畅支持多大的文档？为什么大表格里打字会卡？**

以下数据来自 2026-08 的一次量化基准（无头 Tiptap 实例 + 真实扩展代码，Node 20 环境，预热后取平均值），用于说明各路径的成本量级与相对比例；浏览器中的绝对数值会有差异，但结论一致。

## 每次按键都发生了什么

一次按键会经历两个层面：

1. **引擎层**（ProseMirror）：应用事务、更新文档树、表格相关的 `TableMap` 重算。这层无法跳过。
2. **应用层**（Textory 及接入方）：`onChange` 序列化（`getHTML()` + `toJSON()`）、字数统计（全文 `textBetween` + 正则）、大纲重算（全文 `descendants` 遍历）。

历史上应用层的这些工作**每次按键都同步执行一遍**，全部是 O(全文) 操作。文档小的时候无感，文档一大就变成打字卡顿的主因。

## 基准数据

测试文档三种规模，参照 60fps 的单帧预算 **16.7ms**：

| 每键开销 | 纯文本 1 万字 | 纯文本 4 万字 | 表格 200 行 × 3 列 ≈ 4 万字 |
| --- | --- | --- | --- |
| 旧路径：`getHTML()` 每键一次 | 2.7 ms | 7.3 ms | **67.1 ms** |
| 旧路径：字数统计每键一次 | 1.2 ms | 4.0 ms | 4.8 ms |
| 旧路径：`toJSON` + 大纲遍历 | < 0.1 ms | < 0.1 ms | 0.6 ms |
| **旧路径应用层合计 / 每键** | 4.0 ms | 11.3 ms | **72.5 ms** |
| 引擎层每键（防抖后实际成本） | 1.6 ms | **1.6 ms** | 109.2 ms |
| **旧路径单键总成本** | 5.6 ms | 12.9 ms | **181.7 ms** |
| **防抖后省下 / 每键** | 4.0 ms | 11.3 ms | 72.5 ms |

三个关键事实：

1. **纯文本场景，引擎成本不随文档变大**（1 万字和 4 万字都是约 1.6ms/键）。ProseMirror 打字只改动局部，性能足够好。旧版纯文本 4 万字打字卡，是因为每键多做 11ms 的无用序列化。
2. **表格是序列化最贵的节点**：同样 4 万字，表格的 `getHTML()`（67ms）比纯文本（7.3ms）贵近 10 倍——每个单元格都有独立的属性与嵌套结构。
3. **巨型单表在引擎层就有固定成本**：4 万字单表每键约 109ms 的引擎开销（`TableMap` 随节点重建全量重算 + 表格节点链的对象分配），这是 `prosemirror-tables` 的固有行为，防抖无法消除。

## Textory 内置的防抖优化

针对上述问题，Textory 已做四项优化（2026-08）：

| 优化点 | 做法 | 效果 |
| --- | --- | --- |
| `onChange` 序列化 | 300ms 防抖，输入停顿后统一执行一次 | 打字期间零序列化开销，4 万字表格每键省约 67ms |
| 字数统计 | 防抖 + 按 doc 引用去重，纯光标移动不再计数 | 每键再省 1~5ms |
| 大纲重算 | 防抖，初始加载仍立即计算 | 每键省一次全文遍历 |
| 表格浮动菜单 | 非单元格选区提前返回 | 打字时不再整列遍历、不再每键重渲染菜单 |

防抖的语义对 `onChange` 接入方有两点变化（其余回调同理）：

- 回调在**输入停顿约 300ms 后**触发一次，而不是每键触发；
- **编辑器失焦（blur）、调用 `getData()`、组件卸载时会立即 flush**，autosave 场景不会丢最后一段输入。

## 接入方建议

- **autosave / 受控回写**：直接在 `onChange` 里保存即可，防抖已经内置；不要在自己的 `onChange` 里再对全文档做一次 `getHTML()`/深比较，那会把优化抵消掉。
- **连续输入的停顿点**：防抖后每个输入停顿点会有一次序列化"顿挫"（4 万字表格约 70ms，纯文本 4 万字约 11ms，通常无感）。若业务上仍想消除，方向是序列化进 Web Worker 或增量序列化，目前未内置。
- **`maxCount` 字数上限**：只影响底部状态栏展示（超出标红），不做输入拦截。

## 超大单表怎么办

防抖解决了应用层的重复劳动，但引擎层的 `TableMap` 重算（随单元格总数线性增长）依然存在。经验参考：

- **百行以内**的表格（数千字）：每键引擎成本在几毫秒级，无感；
- **数百行 × 多列**、总字数上万的单表：每键引擎成本可达几十到上百毫秒，打字必然卡顿——这是 ProseMirror 生态的共性问题，不是 Textory 特有；
- 应对方式：**拆分为多张表**、在表格上方用段落分节，或对单表规模做产品层限制。这与 Google Docs 类产品对长表格做分页是同一思路。
